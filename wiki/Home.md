# Sous

Sous (`code-sous`) is a function-execution layer for agent-built automation.
It accepts small, self-contained pieces of code, runs them inside guarded
language runtimes, and exposes them through a stable trigger contract so
that the same function behaves the same way whether it is invoked from a
local developer machine, an HTTP request, a cron entry, or a Cadence
workflow. The platform takes its overall shape from Apache OpenWhisk — a
control plane that manages functions and aliases, a data plane that routes
invocations, and an execution plane that runs untrusted user code under
explicit capabilities — but it makes a small number of opinionated choices
specifically aimed at code generated by AI agents.

Sous accepts function code as UTF-8 text and stores it verbatim, hashed by
content. There is no build step, no container image to bake, and no
deployment pipeline between authoring a function and being able to invoke
it. The same runtime that powers the cluster also powers the `cs` CLI, so
a function that runs locally runs identically under the invoker pool.
Every side effect a function can produce — reading from key-value storage,
publishing to a topic, signing a payload, fetching from an external host —
is declared as a capability in the function manifest, and every trigger
that may reach the function is declared as a role allowlist. This produces
a contract that an agent can reason about: a function cannot quietly
acquire new privileges, and a new version cannot quietly change its
trigger surface.

## What makes Sous distinct

Sous treats functions as text first and bundles second. The canonical
artifact is a directory of source files and a manifest, not an image or a
tarball produced by a build server. Three runtimes implement the same
contract: `cs-js` (powered by `goja`), `cs-python` (a sandboxed
subprocess), and `cs-wasm` (powered by `wazero`). Parity between them is
enforced by a shared test harness so that handler semantics, error
mapping, and capability enforcement do not drift across languages. The
text-first stance is also why publish is cheap: a `cs fn publish` is a
diff over a small set of files, not a multi-minute image rebuild.

Three trigger families converge on the same invoker pool.
`cs-http-gateway` accepts synchronous and asynchronous HTTP invocations,
`cs-scheduler` fires interval and cron triggers, and `cs-cadence-poller`
exchanges activity and decision tasks with a Cadence workflow service.
All four producers emit the same `InvocationRequest` shape onto the
`cs.invoke` topic of `codeQ`, the Kafka-compatible event bus that Sous
uses for fan-out, and they all read `InvocationResult` back from
`cs.results`. Cadence support extends to scheduling and running decision
tasks for workflows that orchestrate activities; child workflows,
signals, and queries are deferred to a future release.

Privileges are explicit and versioned. The control plane records the role
allowlist for each version, the capability set for each version, and the
public keys that may sign bundles. A function publish is rejected if the
bundle is unsigned by a recognized tenant key, if the SBOM is missing, or
if the manifest declares a capability the tenant has not been granted.
The audit trail of these decisions is appended to ledgerDB so that every
control-plane mutation is recoverable and verifiable. The combination of
content-addressed bundles, signed publishes, and capability declarations
gives operators a precise answer to the question "what is running, who
authorized it, and what is it allowed to do?".

## Reading paths

Sous documentation is organized by role. The sidebar on the left lists
every page; the three clusters below are the recommended entry points for
new readers. Each path begins with a brief orientation and ends with a
concrete tutorial so that a reader can confirm understanding by running
something.

### For developers

Developers who want to publish their first function should walk this
path. Start with [Prerequisites](Developers-Prerequisites) to install the
toolchain and credentials, then read [Using Sous](Developers-Using-Sous)
for the conceptual map of packages, functions, versions, aliases, and
triggers. From there, [Getting Started](Developers-Getting-Started) is
the shortest end-to-end exercise.

The reference material for daily work is split across three pages:
[CLI](Developers-CLI) for the command-line surface,
[REST API](Developers-REST-API) for programmatic access, and
[Clients](Developers-Clients) for language SDKs that wrap the REST
surface. Language-specific authoring guides cover
[JavaScript](Creating-Functions-JavaScript),
[Python](Creating-Functions-Python), and
[WebAssembly](Creating-Functions-WebAssembly). When the time comes to
ship something, the [Local Dev to Publish](Tutorial-Local-Dev-to-Publish),
[Promote Through Aliases](Tutorial-Promote-Through-Aliases), and
[Building a Workflow](Tutorial-Building-a-Workflow) tutorials walk
through three representative scenarios end-to-end.

### For operators

Operators who own a Sous deployment should begin with
[Architecture](Operators-Architecture), the canonical system map. The
two deployment guides — [Deployment: Kubernetes](Operators-Deployment-Kubernetes)
and [Deployment: Docker Compose](Operators-Deployment-Docker-Compose) —
cover the two supported topologies; the Kubernetes guide is the
production target and the Docker Compose guide is the lightweight option.

Day-two work is covered by [Administrative Operations](Operators-Administrative-Operations)
and the [Configuration Reference](Operators-Configuration-Reference),
which together describe every operator action and every tunable.
[Observability](Operators-Observability) documents the metrics,
traces, and logs surface. [Security](Operators-Security),
[Runbooks](Operators-Runbooks),
[Capacity and Limits](Operators-Capacity-and-Limits), and
[Migrations](Operators-Migrations) round out the operational lifecycle.
Cross-cutting references for operators are listed under
[Operators: Resources](Operators-Resources).

### For contributors

New contributors should start at
[Project Structure](Contributors-Project-Structure) for an orientation
to the monorepo layout — the services under `cmd/`, the shared libraries
under `internal/`, the schemas under `spec/`, and the roadmap under
`roadmap/`. [What to Contribute](Contributors-What-to-Contribute)
collects the current pickup list, with pointers into roadmap epics and
good-first-issue work.

[Resources](Contributors-Resources) gathers the project conventions:
how this wiki is generated and edited, how commits are structured, how
issues are labeled, and where the design discussion happens. The
[Adding a Runtime](Contributors-Adding-a-Runtime) guide is the reference
for the most common platform extension — wiring up a new language under
the shared capability model, registering it with the invoker pool, and
hooking it into the parity harness.

## Source repository

Sous is developed in the open at
[github.com/osvaldoandrade/sous](https://github.com/osvaldoandrade/sous).
The repository contains the control plane, gateway, scheduler, invoker
pool, Cadence poller, CLI, and runtime adapters in a single Go module.
Issues, the labeled roadmap, and the source for these wiki pages live in
the same repository; see [Reference Roadmap](Reference-Roadmap) for the
current sequencing of work and [Contributors Resources](Contributors-Resources)
for the wiki publishing workflow.
