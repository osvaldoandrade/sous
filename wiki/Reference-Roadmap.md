# Reference: Roadmap

This page is a high-level pointer, not a live status board. The authoritative status of every roadmap item lives in GitHub issues (filter `is:issue label:roadmap`) and in the written specification at [roadmap/README.md](https://github.com/osvaldoandrade/sous/blob/main/roadmap/README.md). The summary below describes the shape of the work the platform is committed to and why each epic exists; check the issues for current progress, owners, and target dates. The link above is one of the few external repository links in this wiki — the GitHub wiki cannot resolve repo paths directly, so paths inside `sous/` are written as fully qualified GitHub URLs the one time they appear.

The roadmap is organised into eight epics across three phases. **Now** (0–2 months) closes out v0.1 and locks the public contract. **Next** (2–5 months) expands the surface — more runtimes, more triggers, real packaging. **Later** (5–9 months) builds platform depth — security hardening, observability, workflow execution. Tasks within an epic are issue-sized (1–2 weeks each); 27 tasks span the 8 epics.

## Now — close out v0.1

**E1 — v0.1 hardening and GA readiness.** This is the epic that takes Sous from `v0.0.0-dev` to a real GA release. It locks the HTTP contract (the lifecycle contract suite at `cmd/cs-control/lifecycle_contract_test.go` is the executable form of the lock), the entity state-machine invariants documented in [Reference-Entity-State-Machines](Reference-Entity-State-Machines), the idempotency contract for synchronous and asynchronous invokes, and the per-tenant rate limit policy at the gateway. The deliverable is a stable contract external agents can rely on without watching for breaking changes — once E1 closes, the manifest schema, the error code catalogue, the invocation envelope, and the lifecycle state machines are versioned and any subsequent breaking change forces a major-version bump.

**E2 — Developer experience and CLI polish.** The first epic that ships once the contract is locked. The `cs` CLI gets first-class scaffolding (`cs new` produces a runnable function in seconds), a one-command publish-and-promote flow that collapses draft upload, publish, alias set, and smoke-test into a single command, and an interactive tail of activations during local development so an author can iterate without leaving the terminal. The Cs CLI is the parity harness's reference client — every test that compares local-and-remote behaviour runs through the same CLI an operator does, so DX improvements here directly raise the floor on every parity test. See [CLI](CLI) for the current surface.

## Next — expand the surface

**E3 — Runtime expansion: Python plus WASM plus parity.** The cs-python adapter (E3.01 is already in main as a subprocess MVP) and the cs-wasm adapter join cs-js under one capability model. Each new runtime ships behind the same `cs.function.script.v1` manifest, the same per-version capability block, and the same `InvocationRequest`/`InvocationResult` envelope, so a function moved from cs-js to cs-python keeps the same external semantics. The parity harness in `internal/runtime/parity` runs the cross-runtime contract: identical event in, identical result out, identical error code on identical failure. Languages are added behind that harness so polyglot does not break the uniform-execution-fabric invariant.

**E4 — Trigger expansion: cron and event sources plus retry/DLQ.** Schedules grow a real cron form (5-field expression, IANA timezone, jitter, overlap policy preserved) so operators stop using `every_seconds` as a poor-man's cron, especially for daily windows that need to honour DST. codeQ topics gain first-class subscription triggers so functions can react to platform events without a polling shim — today tenants who want event-driven behaviour write a glue function that polls a topic and republishes to `cs.invoke`, which doubles cost and breaks the uniform fabric. Every trigger gets a uniform retry policy with a DLQ topic; exhausted retries surface as `CS_RETRY_EXHAUSTED` and increment `cs_invoke_dlq_total{trigger}` so operators can alert on retry exhaustion without per-trigger plumbing. See [Scheduler](Scheduler) and [codeQ-Protocol](codeQ-Protocol).

**E5 — Packaging, dependencies, supply chain.** The cs-js bundler grows publish-time import resolution with a frozen import map: the publisher declares each dependency in `manifest.json` with a URL or in-bundle path plus an optional SRI integrity hash, the control plane fetches and verifies the bytes once, and the runtime resolves `import` statements against the frozen copy with zero network egress at invoke time. Bundles are signed with tenant ed25519 keys (E5.02 has landed) so the invoker can verify provenance against a tenant-scoped keystore before loading. An SBOM in CycloneDX format is attached to every version so downstream supply-chain audits can answer "what was inside version 12" without re-fetching bytes. The combined effect is that a published bundle is auditable end-to-end. See [Security](Security).

## Later — platform depth

**E6 — Security hardening: secrets, egress allowlist, audit.** External secret provider integration (a Vault driver behind the `internal/plugins/secrets` interface) replaces the placeholder env-var path so secret material never enters the bundle, KVRocks, or activation results. Per-tenant network egress gateways layer over the manifest's `http.allowHosts` list so operators can audit and block destinations at the tenant boundary; denials surface as `CS_EGRESS_DENIED` and the activation log names the policy that hit. The audit recorder ships a webhook sink with HMAC signatures so SIEM ingestion needs no shim — the recorder already supports stdout JSON and a codeQ topic, and the webhook completes the triad. See [Security](Security) and [ledgerDB-Audit](ledgerDB-Audit).

**E7 — Observability and operations: sampling, tracing, dashboards, SLOs.** Per-trigger sampling controls (E7.02 already landed) reduce activation record volume without hiding tail latency — a sampling policy on a `Trigger` lets a high-volume HTTP path retain headers and timings while shedding bodies, while a low-volume Cadence path keeps everything. Per-node decision tracing for agent trees lets operators reason about call-chains spanning many activations: an `ActivationRecord` carries `ParentActivationID` and `RootActivationID`, the `/tree` endpoint reconstructs the call graph, and the runtime egress shim injects the `X-CS-Parent-Activation` header so cross-process hops stay linked. Standard Grafana dashboards and the matching SLO definitions ship in `deploy/` so an operator can take Sous from `docker-compose up` to a 99.9% availability target without inventing them. See [Observability](Observability).

**E8 — Cadence workflow depth: DecisionTask, codecs, determinism linter.** The Cadence integration grows beyond Activities. DecisionTask support (E8.01 has landed) lets a `WorkerBinding` with `kind: "workflow"` author a workflow in cs-js whose decisions are produced inside Sous — the workflow function returns a list of decisions (schedule activity, start timer, complete workflow) which the executor in `internal/cadence/workflow` ships back via `RespondDecisionTaskCompleted`. Per-binding input/output codecs (E8.02) let different task lists pin different wire formats (`json`, `msgpack`, `raw`) without sharing a global codec. The determinism linter (E8.03) runs at publish time so workflow bundles cannot call `Date.now`, `Math.random`, `setTimeout`, or any other banned API; replays therefore stay deterministic. See [Cadence-Integration](Cadence-Integration).

## How to read status

Anything labeled `roadmap` on GitHub is on this roadmap. The Markdown spec at the link above is written-once at planning time and does not move; the issue body is the live status board — comments, sub-checkboxes, and scope changes go there. When an epic completes, its issue closes and the task issues auto-close as their checkboxes tick. New work that doesn't fit any epic is filed with `enhancement` first; if it grows, it gets promoted to a roadmap task and the `roadmap` label is added.

## Deliberately out of scope

Billing, metering, and quotas-as-product are separate commercial work. A marketplace for sharing functions across tenants depends on E5 signing and provenance and is not part of this plan. Multi-region active/active control plane depends on E1 contract lock plus E7 SLO baseline. A GUI dashboard for non-agent users follows demand — the CLI and REST API stay first-class.
