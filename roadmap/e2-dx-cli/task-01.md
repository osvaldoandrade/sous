# `cs fn template` library

**Parent epic:** #17
**Phase:** Now
**Estimated size:** M

## Problem
Today `cs fn init <name>` (see `cmd/cs-cli/main.go:139` `fnInit`) only emits a single
hard-coded `function.js` + `manifest.json` pair shaped like an HTTP handler. Agents and
humans starting from common patterns — scheduled jobs, Cadence activities, codeQ
consumers — have to hand-edit the manifest and rewrite the handler stub before they can
test or publish. This raises time-to-first-invocation and obscures which capabilities
each pattern actually needs.

## Proposed solution
- Introduce `internal/cli/templates/` with `embed.FS` packaging one directory per
  template (`http-handler/`, `scheduled-job/`, `cadence-activity/`, `codeq-consumer/`),
  each containing `function.js`, `manifest.json`, and an `README.md` explaining the
  shape of `event`, `ctx`, and required capabilities.
- Refactor `fnInit` in `cmd/cs-cli/main.go` to add a `--template <name>` flag (default
  `http-handler` to preserve existing behaviour) plus `--list` to enumerate templates;
  on `init`, copy the chosen template tree into the target directory and substitute a
  simple `{{.Name}}` token so the manifest's logical name matches the folder.
- Tailor each manifest to the trigger: `scheduled-job` shows `cs.timer` usage and a
  `codeq.publishTopics` capability example; `cadence-activity` shows the activity
  payload contract from `docs/12-cadence-integration.md`; `codeq-consumer` shows the
  subscribe stub and `kv.prefixes` typical for idempotent consumers.
- Add unit tests under `cmd/cs-cli/` that walk every embedded template through
  `bundle.BuildCanonical` and the in-process `runtime.NewRunner` (mirroring `fnTest`)
  with a representative event to guarantee each scaffold is runnable out of the box.
- Update `docs/05-cli.md` with a "Templates" section, the `--list` output, and a
  worked example for each template.

## Acceptance criteria
- [ ] `cs fn init <name> --template http-handler|scheduled-job|cadence-activity|codeq-consumer`
      produces a directory whose `function.js` + `manifest.json` pass `cs fn test`
      against the bundled sample event with `status=success`.
- [ ] `cs fn init --list` prints the available template names, one per line, with a
      one-line description sourced from the template's `README.md`.
- [ ] Templates live under `internal/cli/templates/` and are compiled in via
      `//go:embed`; no runtime filesystem lookup or network call is required.
- [ ] An unknown `--template` value returns a non-zero exit, a `client error` (exit
      code 1), and a message listing the available templates.
- [ ] `docs/05-cli.md` documents the new flag, lists the templates, and shows the
      capability stanza generated by each one.
- [ ] Go test coverage exercises each template end-to-end (canonical bundle + runner)
      and a snapshot test asserts manifest shape (runtime, entry, handler, limits).

## Dependencies & risks
- Depends on the existing `bundle.BuildCanonical` and `runtime.NewRunner` plumbing
  used by `fnTest`; no API changes required on the control plane.
- Risk: drift between template capability stanzas and what
  `internal/runtime/providers.go` enforces — mitigate with the end-to-end runner test.
- Risk: `--template` name collisions if the registry grows — keep names short, scoped
  to trigger type, and add a deprecation note pattern in the README skeleton.

## Out of scope
- Custom user-supplied templates (filesystem or Git-hosted) — tracked separately.
- Multi-file function bundles beyond `function.js` + `manifest.json`.
- Language runtimes beyond `cs-js` (no Python/WASM templates yet).
- A `cs fn template publish` / share-back workflow.
